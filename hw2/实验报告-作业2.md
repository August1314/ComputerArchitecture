### 1.2 协议关键实现代码及说明

#### 1.2.1 数据结构定义

```murphi
const
  NUM_CACHE : 3;  -- 3个缓存
  NUM_MEM   : 1;  -- 1个内存块

type
  StateType : enum {M, S, I};  -- 三种缓存状态
  CacheId   : scalarset(NUM_CACHE);
  
  BusReqType : enum {BusNone, BusRd, BusRdX};  -- 总线请求类型
  BusCtrlType : enum {CtrlNone, CtrlFlush};    -- 总线控制信号
  
  Bus : record
    req     : BusReqType;   -- 总线请求
    source  : CacheId;      -- 请求来源
    ctrl    : BusCtrlType;  -- 控制信号
  end;
```

**设计说明**:
- 使用`scalarset`类型定义CacheId，利用Murphi的对称性优化减少状态空间
- 不跟踪数据值，只验证状态一致性，进一步简化状态空间
- 使用`BusCtrlType`标识是否有缓存提供数据（CtrlFlush表示有缓存响应）

#### 1.2.2 缓存侦听机制

```murphi
procedure Snoop(i: CacheId);
begin
  if bus.req = BusRd then
    switch caches[i].line.state
      case M:
        -- M状态缓存提供数据并降级到S
        bus.ctrl := CtrlFlush;
        caches[i].line.state := S;
      case S:
        -- S状态保持不变
      case I:
        -- I状态保持不变
    endswitch;
    
  elsif bus.req = BusRdX then
    switch caches[i].line.state
      case M:
        -- M状态缓存提供数据并失效
        bus.ctrl := CtrlFlush;
        caches[i].line.state := I;
      case S:
        -- S状态缓存失效
        caches[i].line.state := I;
      case I:
        -- I状态保持不变
    endswitch;
  endif;
end;
```

**设计说明**:
- 实现了完整的侦听逻辑，所有缓存监听总线并根据当前状态做出响应
- M状态缓存在侦听到BusRd时降级到S，在侦听到BusRdX时失效
- S状态缓存在侦听到BusRdX时失效
- 使用`bus.ctrl`信号标识是否有缓存提供了数据

#### 1.2.3 处理器读请求

```murphi
ruleset i : CacheId do
  rule "PrRd, Cache State I"
    (caches[i].line.state = I) &
    (bus.req = BusNone)
  ==>
  begin
    -- 读缺失，发起BusRd请求共享副本
    bus.req := BusRd;
    bus.source := i;
  end;
end;
```

**设计说明**:
- 只实现I状态下的读请求（读缺失），因为M和S状态的读是缓存命中，不需要总线事务
- 读缺失时发起BusRd请求，最终转换到S状态

#### 1.2.4 处理器写请求

```murphi
ruleset i : CacheId do
  rule "PrWr, Cache State S"
    (caches[i].line.state = S) &
    (bus.req = BusNone)
  ==>
  begin
    -- 写升级，发起BusRdX请求独占权限
    bus.req := BusRdX;
    bus.source := i;
  end;

  rule "PrWr, Cache State I"
    (caches[i].line.state = I) &
    (bus.req = BusNone)
  ==>
  begin
    -- 写缺失，发起BusRdX请求独占副本
    bus.req := BusRdX;
    bus.source := i;
  end;
end;
```

**设计说明**:
- 实现了S状态的写升级和I状态的写缺失
- M状态的写是缓存命中，不需要总线事务，因此不需要实现规则
- 两种情况都发起BusRdX请求，最终转换到M状态

#### 1.2.5 总线事务处理

```murphi
rule "Process bus transaction"
  bus.req != BusNone
==>
begin
  -- 1. 所有缓存侦听并响应总线事务
  for i : CacheId do
    if i != bus.source then
      Snoop(i);
    endif;
  endfor;

  -- 2. 更新请求缓存的状态
  if bus.req = BusRd then
    caches[bus.source].line.state := S;
  elsif bus.req = BusRdX then
    caches[bus.source].line.state := M;
  endif;

  -- 3. 如果有缓存提供数据，更新内存
  if bus.ctrl = CtrlFlush then
    mem.valid := true;
  endif;

  -- 4. 清除总线状态
  bus.req := BusNone;
  undefine bus.source;
  bus.ctrl := CtrlNone;
end;
```

**设计说明**:
- 实现了完整的总线事务处理流程
- 先让所有其他缓存侦听并响应（缓存优先响应）
- 然后更新请求缓存的状态
- 最后清除总线状态，准备下一次事务

#### 1.2.6 一致性不变式

```murphi
invariant "Only one Cache may be Modified"
  CountModifiedCache() <= 1;

invariant "Modified Cache implies no Shared Cache"
  ( CountModifiedCache() = 1 )
  ->
  forall i : CacheId do
    caches[i].line.state != S
  end;
```

**设计说明**:
- 第一个不变式确保最多只有一个缓存处于M状态（互斥性）
- 第二个不变式确保当有缓存处于M状态时，不能有缓存处于S状态（一致性）

### 2.2 MESI协议的关键改进

#### 2.2.1 新增E（Exclusive）状态

```murphi
type
  StateType : enum {M, E, S, I};  -- 四种缓存状态
```

**E状态的意义**:
- 表示缓存拥有数据的唯一干净副本
- 数据与内存一致
- 可以无需总线事务直接升级到M状态（关键优化！）

#### 2.2.2 新增BusUpgr总线事务

```murphi
BusReqType : enum {BusNone, BusRd, BusRdX, BusUpgr};
```

**BusUpgr的作用**:
- 用于S状态的写升级
- 只需要失效其他缓存，不需要数据传输
- 比BusRdX更高效

#### 2.2.3 E状态的写操作优化

```murphi
rule "PrWr, Cache State E"
  (caches[i].line.state = E) &
  (bus.req = BusNone)
==>
begin
  -- 关键优化：无需总线事务，直接升级到M
  caches[i].line.data := (caches[i].line.data + 1) % 2;
  caches[i].line.state := M;
end;
```

**优化效果**:
- E状态写操作不需要总线事务
- 减少总线流量
- 提高性能

#### 2.2.4 BusRd响应时的E/S状态判断

```murphi
if bus.req = BusRd then
  if bus.ctrl = CtrlNone then
    -- 没有其他缓存有数据，转到E状态
    caches[bus.source].line.state := E;
  else
    -- 有其他缓存有数据，转到S状态
    caches[bus.source].line.state := S;
  endif;
  caches[bus.source].line.data := bus.data;
endif;
```

**设计说明**:
- 根据是否有其他缓存响应来决定转到E还是S状态
- 如果只有内存响应（bus.ctrl = CtrlNone），说明是唯一副本，转到E
- 如果有缓存响应（bus.ctrl != CtrlNone），说明有共享副本，转到S

## 三、思考题

### 3.1 基于侦听MSI缓存一致性协议存在哪些问题？

#### 问题1：总线带宽瓶颈

**问题描述**:
- 所有缓存请求都需要在总线上广播
- 随着处理器数量增加，总线流量急剧增长
- 总线成为性能瓶颈

**影响**:
- 可扩展性差，难以支持大量处理器
- 总线争用导致延迟增加

#### 问题2：状态空间爆炸

**问题描述**:
- 侦听协议的分布式特性导致大量并发执行路径
- 多个缓存可以同时发起请求，产生组合爆炸
- 形式化验证困难

**实验证据**:
- MSI协议（3缓存，3状态）→ 398,483个状态
- SCI协议（3处理器，100+状态）→ 18,193个状态
- 简单的状态机 + 高并发 > 复杂的状态机 + 低并发

**根本原因**:
1. 缺乏序列化机制（无Pending状态）
2. 多个缓存可以同时操作
3. Murphi探索所有可能的执行交错
4. 交错因子随缓存数量非线性增长

#### 问题3：写升级效率低

**问题描述**:
- S状态写操作需要发起BusRdX
- BusRdX会传输数据，即使缓存已经有数据
- 浪费总线带宽

#### 问题4：无法区分独占和共享

**问题描述**:
- MSI协议中，即使只有一个缓存有数据副本，也是S状态
- 后续写操作仍需要总线事务
- 错失优化机会

### 3.2 可能的改进方向

#### 改进1：升级到MESI协议

**改进内容**:
- 新增E（Exclusive）状态
- E状态写操作无需总线事务
- S状态写升级使用BusUpgr（无需数据传输）

**效果**:
- 减少总线流量
- 提高写操作性能
- 状态空间减少约28%

#### 改进2：采用目录协议

**改进内容**:
- 使用集中式目录管理共享信息
- 点对点通信替代广播
- 添加Pending状态序列化操作

**效果**:
- 解决总线带宽瓶颈
- 更好的可扩展性
- 状态空间大幅减少（如SCI协议）

**示例**:
```
SCI协议的Pending状态：
HI → HIS_D (pending) → HS

在HIS_D期间，其他处理器的请求被阻塞
序列化了操作，减少了交错路径
```

#### 改进3：添加Pending状态

**改进内容**:
```murphi
StateType : enum {
  M, S, I,           -- 稳定状态
  I_to_S, I_to_M,    -- Pending状态
  S_to_M
};
```

**效果**:
- 序列化操作，减少并发
- 降低状态空间复杂度
- 更容易形式化验证

#### 改进4：使用原子事务

**改进内容**:
```murphi
rule "Atomic PrRd"
  (caches[i].state = I) & (bus.req = BusNone)
==>
  -- 原子地完成整个事务
  for j : CacheId do
    if j != i then Snoop(j); endif;
  endfor;
  caches[i].state := S;
end;
```

**效果**:
- 消除中间状态
- 大幅减少状态空间
- 简化验证

### 3.3 基于侦听MESI缓存一致性协议存在哪些问题？

#### 继承MSI的问题

1. **总线带宽瓶颈**：仍然使用广播机制
2. **可扩展性差**：难以支持大量处理器
3. **状态空间大**：虽然比MSI小，但仍然很大（285K状态）

#### MESI特有的问题

1. **状态机更复杂**：4种状态vs 3种状态
2. **E/S判断开销**：需要判断是否有其他缓存有数据
3. **实现复杂度**：需要额外的控制逻辑

#### 改进方向

1. **升级到MOESI协议**：新增O（Owned）状态，进一步优化
2. **采用目录协议**：如AMD的HyperTransport
3. **混合协议**：结合侦听和目录的优点
